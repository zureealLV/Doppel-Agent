## 为什么先修取消，而不是继续堆 fixture

`d1593e9` 的本地 Python **322 passed, 1 skipped**，但
[原始 CI 36704670719](https://github.com/zureealLV/Doppel-Agent/actions/runs/36704670719)
在 Windows Python 3.11 的重复 checkpoint/API 取消门禁失败：请求已取消，
数据库仍为 `running`。3.12 被矩阵 fail-fast 取消，不计为通过。失败记录
保留，未重跑、删门禁、延长等待或忽略异常来刷绿。

源码显示 create/resume 的 running 写入、事件、runtime 初始化在取消处理
之外。仅把初始化移入 try 还不够：完成事件/结果写入也在 try 之外，且
`to_thread` 取消不等于 SQLite 工作停止；迟到的 running/completed 写入
可能覆盖取消终态。另一个窗口是调度任务已登记、协程还没执行第一步，
此时 task.cancel 会跳过 operation 内的整个 try/finally。

## 修补与确定性证据

- create/resume 从 token 检查到最终结果落库均纳入异常边界。
- owned persistence/event 写入 shield + drain；先等迟到写入，再发布取消
  终态。取消收尾本身也由 owned task 完成，反复取消不能遗弃终态写入。
- scheduler 记录 operation entry；首次执行前只置 token，让 operation
  进入自己的异常处理；进入后仍使用真实 task cancellation。shutdown
  遵守同一边界。未模拟模型事件、未给任意代码增加强 OS 沙箱声明。
- 新增 **15 项** gate 测试：create/resume running update、初始事件、runtime
  初始化、completion update/event；首次执行前 cancel/shutdown；取消收尾
  再取消一次/两次。真实 SQLite 线程由 owned Event 精确卡在边界，断言
  scheduler future 等待完成、数据库终态、唯一 `run.cancelled` 事件和无
  活跃任务。没有用短 sleep 来猜测取消窗口。
- 先观察 **5 项初始化红测、4 项完成红测、2 项首次执行前红测**，再修补。
  完成阶段的 runtime 是明确 deterministic stub，不是模型质量证据。

此范围只声明 RunService 根任务边界；不外推全部 subagent、任意 DB/事件
写入失败或所有 GUI 关闭场景均已覆盖。旧 checkpoint/MCP 修补保留。
