# Doppel Agent v0.14.2 更新与测试报告

日期：2026-09-30。范围：原 v0.15 计划新补充的 **Task 3D — checkpoint
取消生命周期 hotfix**，并保留 v0.14.1 的六个评测安全门禁。
这不是 v0.15 完整矩阵，也不是 v1.0 完成声明。

## 发现、复现与根因

v0.14.1 分支 CI 的 Windows Python 3.11/3.12 各 237 tests 通过，随后推 tag；
但 [标签 CI 36685070975](https://github.com/zureealLV/Doppel-Agent/actions/runs/36685070975)
Python **3.12.10** 出现 **1 failed, 236 passed**。失败不是模型结果，
而是 `RunsApiTests.test_cancel_running_async_provider_emits_one_terminal_event`
收尾 `rmtree` 遇到 `checkpoints.sqlite3` 的 **WinError 32**。

源码审查发现：aiosqlite **0.22.1** 在 worker thread 获取真实 SQLite
connection，再通过 Future 把它赋给 proxy；如果获取 Future 被取消，
真实连接可以已创建，但 proxy 尚未持有它，原 context manager 没有可关闭
的 connection。这会遗弃句柄并依赖 GC，Windows 上文件仍可被占用。

为证明此路径，新增可重复的 **实际 SQLite connector** 闸门：worker
已经持有真实连接但暂停返回，调用方此时取消，再释放 worker。原实现
确定性红测 **1 failed**，断言为“取消后的获取遗弃了 live SQLite handle”。
不是给 `rmtree` 加重试，也不是认为 CI 随机出错就重新运行同一红提交。

## 修补

`src/doppel_agent/persistence/checkpoints.py` 明确拥有异步获取和关闭任务：

- acquisition 使用 shield；如果调用方取消，先 drain 获取，再关闭实际
  connection，然后传播取消，不能让 worker 的连接结果丢失。
- close 同样 shield/drain；再次取消不能中断资源收尾，close 中取消仍保留
  cancellation，不能误返回成功。
- 初始化 PRAGMA/commit 失败也关闭已获取 connection；获取失败正常保持
  原异常，已经取消的调用则保持取消语义。
- Graph/Deep 继续共用这个 checkpointer；WAL、foreign keys、busy timeout、
  strict msgpack 与 checkpoint/resume 内容不变。没有升级依赖或加入新服务。

取消等待 owned SQLite 工作完成，不宣称可以强杀正在执行的 SQLite thread。
这个修补不改变 legacy 同步 Provider/工具的取消能力边界，不外推全 runtime
能力 parity。新 EXE 放独立目录；不覆盖旧日常包。
