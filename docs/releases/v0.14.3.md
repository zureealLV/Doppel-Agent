- Graph 工厂默认只有读工具；RunService 注入 patch、命令、MCP，并负责

- Deep 没有独立 command/execute；command grant 只启用批准 patch 后的
  verification，因此无法做“修补前先运行失败测试”的 TDD 协议。

  runtime 内存中；approve 实测报 `propose_patch must be prepared before
  execution`，没有覆盖外部修改。它需要调用方另存元数据，不能视为工厂
  自有 durable reviewed approval。RunService 会单独持久化该元数据。
- Legacy 的普通写文件、同步 approval、MCPBridge 不等同 reviewed patch、
  durable resume、可取消 Core worker 或生产 MCPToolExecutor gateway。
- nav-04 目前只要求源码导航，不要求执行 MCP。历史 extra grant 保留并
  显式标注；其 fixture/授权变更要在 Task 5B 单独版本化。

Live context 在请求前冻结 contract hash/version、边界、原/可用/排除分母
与精确 selected keys。旧 context 或变化后的 selection 不能续跑，必须换
输出目录。仍只允许 9 导航/12 盲审 canary，**full guard 不解除**。

## 新测试暴露的问题与修补

真实本地 stdio MCP server 经 RunService/scheduler 调用，发现旧 custom
tool 单元测试未覆盖的两处红测：

1. Graph registry 没把已授予的 `mcp_execute` 加入 allowed capabilities；
   即使 executor 已授权，批准后仍 `capability denied: mcp_execute`。
   修补 service registry 授权集合，未授权路径继续不注入 MCP tools。
2. Connector 在 run scheduler 任务里进入 SDK AnyIO cancel scope，而
   shutdown 在另一个任务里 `aclose`，出现“exit cancel scope in a different
   task”。每个 connector 现在有独立 lifetime owner，进入/退出都在同一
   task，调用者只共享 session。启动取消、重复取消、整个 manager 的关闭
   都先 drain owned work；关闭一处失败也继续关闭其余 owner，再抛聚合错误。

额外关闭取消红测原本仅关闭第一个 server；close-error 红测也遗弃第二个
owner。两者都有确定性 gate，已修复；没有忽略异常、放宽 cleanup 断言或
禁用安全软件。Deep 工厂 metadata 限制是明确的能力排除，不伪装已修补。
