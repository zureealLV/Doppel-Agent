# Doppel Agent v0.15 Live Runtime Matrix Implementation Plan

> **For Hermes:** Execute this plan task-by-task locally; do not delegate unless the user explicitly asks for delegation.

**Goal:** Build a reproducible real-model evaluation protocol without turning mock plumbing, keyword signals, or incomplete runs into task-quality scores.

**Architecture:** Keep the frozen 20-case manifest and three runtime modes. Add an append-only per-run result store, immutable config/commit snapshot, sanitized failure taxonomy, token/cost accounting, and a serial read-only canary. Block the 180-run full matrix until all cases have seeded workspaces, executable validators, and equivalent runtime capabilities. Separate deterministic checks from human adjudication.

**Tech Stack:** Python 3.11+, existing OpenAI-compatible Provider, LangGraph 1.x, Deep Agents 0.x, SQLite checkpoints, pytest, Ruff. No new service dependency.

## Evidence audit before paid execution

- `bench/cases/runtime/manifest.json` has 20 prompts and 180 planned run keys, but it does **not** define per-case source fixtures or expected patch/test outcomes. A keyword or event match is a diagnostic signal, not a task score.
- `graph` currently exposes a focused read-only tool set; `legacy` and `deep` have different write/approval/MCP/cancellation semantics. Comparing those categories today would conflate runtime capability with model quality.
- Only `nav-01`, `nav-02`, `nav-03` are enabled for the first 9-run read-only canary. It copies Git-tracked `src/doppel_agent` from one clean commit into a fresh temporary workspace per run. The live-model result remains pending human review.
- No API credential is configured in the current process. Do not call a paid model or claim canary completion until `DOPPEL_AGENT_API_KEY`, model, URL, prices, and budget are provided.

## Task 4 — Real 9-run canary (pending credentials and prices)

Prerequisites: clean committed checkout, `DOPPEL_AGENT_API_KEY`, an HTTPS OpenAI-compatible URL, exact model name, and the provider's input/output USD-per-million-token prices.

```powershell
$env:DOPPEL_AGENT_API_KEY = '<local secret; never commit>'
uv run --extra agent python -m bench.live_runtime_matrix `
  --mode canary `
  --base-url '<provider API base URL>' `
  --model '<exact model>' `
  --input-price-per-million <rate> `
  --output-price-per-million <rate> `
  --max-cost-usd <stop-between-runs threshold> `
  --output-dir .bench-results/live-canary-v015
```

The threshold is checked between runs; a single request can overshoot it. Confirm the Provider's own hard spending cap separately. Never put the API key in a CLI argument or report. Run the same command to resume; do not delete partial failures. Manually review every answer before any quality claim.

## Task 5 — Ground all 20 cases before unlocking 180 runs (pending)

Files: `bench/cases/runtime/manifest.json`, new per-case fixture directories under `bench/cases/runtime/fixtures/`, `bench/live_runtime_matrix.py`, new tests.

1. For each review case, seed a distinct vulnerable file and hidden answer key; test the flaw independently.
2. For each TDD/patch case, specify a frozen base tree, allowed edits, failing/passing tests, and expected diff constraints.
3. For approval cases, script the exact decision and assert one resume and zero unapproved side effects.
4. For MCP cases, provide an isolated server fixture and expected structured response/error behavior.
5. For cancellation, provide a bounded process fixture and assert no surviving child.
6. Define a capability matrix. If a runtime cannot execute a task, mark it `unsupported` in the protocol instead of counting it as model failure; change the denominator explicitly and version the protocol.
7. Add executable validators and manual-review forms. Freeze before calling the model.

Acceptance: 20 independently reproducible cases, documented capability parity or an explicit revised denominator, and no leaked answer keys inside Agent workspaces.
